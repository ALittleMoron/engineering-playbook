## README files

- Treat README files and their translations as concise entry points for their intended audience, not
  as replacements for comprehensive documentation.
- Follow the repository's established structure, audience, contribution model, and maintainer
  conventions. Do not impose one project's README template on unrelated, work, or third-party
  repositories.
- Include the information needed to understand the repository's purpose and scope, its meaningful
  capabilities or responsibilities, relevant technologies or requirements, and the shortest common
  path to installing, running, testing, or using it. Retain legal, governance, support,
  compatibility, and community sections when the repository requires them.
- Describe capabilities in terms of meaningful user or developer value. Do not present routine
  integrations, baseline engineering practices, or low-level implementation details as
  distinguishing features unless they are essential to understanding or using the repository.
- Keep getting-started instructions focused on the normal workflow. Avoid exhaustive command
  catalogs, advanced variants, and narrowly scoped operational procedures.
- Move detailed architecture, operations, API references, troubleshooting, and other specialized
  material to focused documentation when the repository has an appropriate documentation location.
- Preserve useful existing presentation and metadata, including tables, badges, status or coverage
  indicators, branding, navigation links, and compatibility information, unless they are obsolete,
  incorrect, or explicitly requested to change.
- Keep translated README variants equivalent in meaning while allowing natural differences in
  language and phrasing.
